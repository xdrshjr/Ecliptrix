# 特效时长逐键输入 0.8 秒，成品只有 17 帧

## 问题描述

在特效工作台，用户把「时长（秒）」从 5 改成 0.8，输入框会在第一下按键时提前改写数字。按通常顺序键入 `0`、`.`、`8` 并离开字段，界面显示 `0.567`，草稿显示「已保存」。以 30 fps 计算，用户要求的是 24 帧，实际生成的 MP4 只有 17 帧，少了 7 帧。三次独立从 5 秒开始输入均复现。

验证环境为 Windows、源码基线 `2b92d136`、1440 × 940 的 Chromium 窗口、Next.js 开发界面、独立 FastAPI/SQLite 及本地 Remotion 渲染服务。验证覆盖从新建项目到生成视频并插入时间线。桌面安装包和整条时间线的最终导出尚未验证。

## 复现步骤

1. 新建测试视频项目。从素材面板底部点「特效」，在模板分类中选「倒计时」，再点「圆环倒计时」。使用默认的 5 秒，等顶部出现「已保存」。
2. 在右侧「画布 → 时长（秒）」中按 Ctrl+A，依次按主键盘的 `0`、`.`、`8`，然后按 Tab。观察每次按键后的输入框。实测依次是 `0.5`、`0.5`、`0.567`，预览底部显示 `30 fps · 0.57 s`。预期输入结束后为 `0.8`，预览为 `0.80 s`。
3. 等顶部显示「已保存」，聚焦标题栏「关闭」按钮按 Enter，再从素材面板重开。时长仍为 `0.567`。点击「生成视频」，展开「最近生成」，待任务显示「已生成」后点「在新视频轨插入」。时间线上出现一个标为 `0.6s` 的特效片段。
4. 做对照时，在同一草稿同一字段一次性填入完整值 `0.8`。本次使用 Playwright 的 `fill`，两次都得到 24 帧。以下片段可在已打开上述工作台的 Python Playwright 会话中直接运行，比较两种输入路径。

```python
from playwright.sync_api import expect

studio = page.locator("[data-effects-studio]")
duration = studio.get_by_role("spinbutton", name="时长（秒）", exact=True)
header = studio.locator("header")
for method in ("逐键输入", "整值输入"):
    duration.fill("5")
    duration.press("Tab")
    expect(header).to_contain_text("已保存")
    if method == "逐键输入":
        duration.press("Control+a")
        for key in "0.8":
            duration.press(key)
            print(key, duration.input_value())
    else:
        duration.fill("0.8")
    duration.press("Tab")
    expect(header).to_contain_text("已保存")
    print(method, duration.input_value())
```

## 根因分析

**第一个偏差发生在输入框收到 `0` 时。** 工作台将当前草稿传给 `EffectsInspector`（`src/components/video/effects/EffectsStudioModal.tsx:185–192`）。「时长（秒）」使用共享控件 `NumberField`，每次收到有限的 `valueAsNumber` 就限幅，再由父组件取整到帧并调用 `draft.edit`（`src/components/video/effects/EffectsInspector.tsx:18–19、120–140`）。输入 `0` 会立即写入下限 0.5 秒，即 15 帧；受控输入框随即从草稿反算并显示 `0.5`。原始记录采集的是每次按键**之后**的输入框值。末位 `8` 追加到 `0.5` 的解释与结果吻合：若事件值为 `0.58`，则 `Math.round(0.58 × 30) = 17`，回显 `0.567`。`0.58` 是推算值。首键回显 `0.5`、末键回显 `0.567` 均有直接记录。

| 同一草稿的操作 | 真实响应或界面观测 | 结果 |
|---|---|---|
| 从 5 秒逐键输入，三次 | PUT 200，草稿版本 2、5、8 均返回 `document.duration_frames = 17` | 每次字段均显示 `0.567` |
| 在两次故障后一次性填入 `0.8` | PUT 200，草稿版本 3、6 均返回 `document.duration_frames = 24` | 每次字段均显示 `0.8` |
| 重开最后一次逐键输入的草稿 | GET 200，版本 8 | 字段显示 `0.567` |
| 生成版本 8 并插入新轨 | 渲染任务「已生成」，时间线片段数由 0 变为 1 | FFprobe 解码 17 帧 |

原始记录位于本轮工作目录 `.agentmesh/task-tge-446712a4-7641-4f55-9098-8957288fcff4/scratch/round2-duration/`。其中 `repro.py:16–41` 记录字段标签、逐键读值和成功 PUT 响应中的帧数。`observed.txt:1–30` 显示，同一草稿、同一模板、同一倒计时参数 `from=5` 下，仅改变输入方式就能在 17 帧与 24 帧之间重复切换。`observed.txt:38–47` 记录重开、生成版本和上轨结果。时间线的 `0.6s` 只精确到一位小数。

评审时只读核对了该目录的 `test.db`。沿 `effect_render_jobs.draft_id → effect_drafts.id` 及 `result_asset_id → effect_assets.id` 关联，草稿版本与任务引用版本均为 8，草稿文档及任务的 `request_json.render_snapshot.document.duration_frames` 均为 17。成功任务的资产指向 `outputs/9461ccad-a6ab-4a26-9eae-af2073bcccf4/video.mp4`。对这个文件重新执行下述 FFprobe 命令，得到 30 fps、17 帧。偏差在首键后已可见，在提交渲染前已经保存，预览格式化和编码器均无法解释首键偏差。24 帧对照验证到草稿保存为止。

草稿编辑会把新的工作文档标记为待保存（`src/components/video/effects/useEffectsDraft.ts:128`），自动保存延迟为 500 毫秒（同文件第 241 行）。17 帧在允许的 15–1800 帧范围内（`src/lib/effects/validation.ts:25`），因此能正常保存。预览播放器直接使用草稿的 `durationFrames`（`src/components/video/effects/EffectsPreview.tsx:34`），「生成视频」先保存再提交该草稿版本（`src/components/video/effects/useEffectsController.ts:299`）。这解释了错误时长如何一路进入成品。

对这次生成的 MP4 执行下列命令，将末尾文件名替换为实际成品路径：

```powershell
ffprobe -v error -count_frames -select_streams v:0 -show_entries stream=codec_name,r_frame_rate,duration,nb_read_frames -of default=nw=1 "video.mp4"
```

```text
codec_name=h264
r_frame_rate=30/1
duration=0.566667
nb_read_frames=17
```

## 影响面

- **已验证**：在可编辑时长的工作台中，合法的亚秒时长会被改短并保存。预览、重开后的草稿、生成视频和时间线片段均沿用该值。对于按音乐节拍安排特效的用户，本例片段短了约 233 毫秒。
- **从调用点推断**：字号缩放的下限是 0.6，动画速度的下限是 0.5，两者也使用相同控件（`src/components/video/effects/EffectsInspector.tsx:70`、`src/components/video/effects/EffectsInspector.tsx:76`）。输入以零开头的小数时也存在首位被改写的条件。两者的下游表现尚待分别验证。

## 候选修复方案

| 方案 | 改动范围 | 风险 | 预计工作量 |
|---|---|---|---|
| A．让共享数值框保留正在输入的文本 | 在 `NumberField` 内保存编辑中的原文，失焦或按 Enter 时一次性校验并提交；时长沿用现有帧换算。未更改的值跳过提交 | 中低。需处理外部撤销、草稿或模板切换、方向键步进，以及仍在输入时点击「生成视频」的提交顺序 | 小，集中在一个前端控件和定向回归 |
| B．仅为时长提供独立的秒数编辑框 | 在画布区为秒数单独保留输入文本，提交时换算成帧 | 低。局部改动容易验证，但缩放和速度仍共用现有的逐键限幅机制，需要另行处理 | 小，增加一套数值编辑逻辑 |

## 推荐修复与验收

推荐 **A**。问题起点是共享数值框在用户仍在输入时回写下限。把校验推迟到明确的提交时机，可以保留现有草稿格式、合法帧范围和渲染流程。空值、未写完的小数及越界值应有一致的纠正反馈，避免把临时值静默写入草稿。

验收时应从 5 秒分别逐键输入和一次性填入 `0.8`，两条路径都应保存 24 帧。再分别通过 Tab、Enter 和直接点击「生成视频」提交，确认预览、重开后的时长和 MP4 解码帧数一致。额外检查编辑时停顿超过 500 毫秒、方向键单帧步进、撤销重做以及只读或替换模式下的时长锁定，确保输入中的首位不会进入自动保存。

## 评审结论

**采用方案 A，在特效检查器的共享 `NumberField` 内保留编辑文本，失焦或按 Enter 时提交一次。** 方案 B 能修复已复现的时长错误，但字号缩放与速度也会把首键 `0` 提升到正下限。三个字段共用同一个输入处理函数，修正这一处即可覆盖共同原因。帧换算留在时长调用点，现有草稿版本、保存队列和渲染接口已能准确传递提交的帧数。

| 边界 | 实现与验收要求 |
|---|---|
| 输入与校验 | 键入 `0` 后停顿超过 500 毫秒，再补上 `.8`。提交前应保留编辑状态，草稿仍为原帧数。提交有效数值时沿用字段范围，有限越界值在提交时限幅并回显；清空、无法解析的文本或整数参数的小数应恢复上次有效值并给出可见反馈。时长沿用四舍五入到帧的规则。模板数值含整数和数组项，各自的约束见 `src/lib/effects/validation.ts:39–51`。 |
| 生成、撤销与失败 | 从输入框直接点「生成视频」，须在 `draft.flush()` 前把 24 帧同步交给 `draft.edit`。检查渲染任务引用的新版本和成品 24 帧；保存失败时沿用现有错误提示，不能生成旧版本。Enter 后再 Tab、只聚焦后失焦、输入另一个折算到同一帧的秒数，均不应新增重复历史。一次有效修改应能一次撤销回 5 秒。现有 `edit` 每次都会记录历史，见 `useEffectsDraft.ts:128–134`；生成入口见 `useEffectsController.ts:295–304`（均位于 `src/components/video/effects/`）。 |
| 外部更新与锁定 | 同一草稿的保存响应或普通重绘应保留尚在输入的文本。切换草稿或模板、撤销重做、进入只读或替换锁定时，应以当前文档和权限为准，防止旧字段失焦后覆盖新值；两个草稿时长相同也要检查。工作台拦截 Ctrl/Cmd+Z，模板切换会重置参数，见 `EffectsStudioModal.tsx:73–79、188–193` 和 `useEffectsController.ts:284–294`。 |
| 方向键与共享字段 | 保留数值框的步进和键盘可操作性。在 17 帧处分别向上、向下步进并提交，核对 18、16 帧及上下界 15、1800 帧；三位小数的回显不能改变步进单位。对缩放、速度各做一次逐键小数输入，再抽查下限为零的强度、整数参数和数组项，防止共享改动改变合法值。调用点见 `EffectsInspector.tsx:70–104、120–140`。 |

## 修复复核

修复后，数值框在编辑期间保留浏览器中的输入。时长只在提交时换算成整数帧。逐键输入首位 `0` 后停顿 800 毫秒，草稿仍为 5 秒；补全 `.8` 后按 Tab，草稿保存为 24 帧。重复提交折算到同一帧的秒数没有增加草稿版本。从 17 帧按上、下方向键分别得到 18 帧和 16 帧。

复核时发现，数值框仍有焦点时按 Esc 会先触发工作台关闭，跳过失焦提交。新增回归测试在修复前缺少「关闭前保存修改？」对话框。修复后，工作台先接收字段值，再按最新草稿状态决定是否提示保存。实测选择「保存并关闭」后重新打开，时长为 0.8 秒。

在 Chromium 中从时长框直接点「生成视频」，任务引用的草稿版本为 19，保存值为 24 帧。FFprobe 解码成品为 30 fps、24 帧、0.800 秒，插入新轨后的片段也显示 0.8 秒。
