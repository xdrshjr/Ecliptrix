# 诊断报告：「搜索在线视频」弹窗三栏布局错位

> **Bug slug**：`video-search-modal-layout-misalignment`
> **节点**：Subtask #0（问题定位与根因分析）。**本节点只产出诊断，不改修复代码、不 commit。**
> **评审**：Subtask #1 已对本文做根因证据与方案审计，结论见文末 **§九 评审结论**；正文中被评审修正/新增的段落都以「**本评审修正**」「**（评审新增）**」标记。
> **日期**：2026-10（第 1 轮诊断）
> **需求原文**：「项目的这个搜索视频素材的弹窗，现在显示布局混乱，错位，需要完善修复，顶级产品」
> **用户附件**：`.agentmesh/attachments/paste-1795506718248.png`（1285×1011，弹窗截图）

## 结论一句话

弹窗并不是「某个 CSS 写错了一处」而乱，而是**三栏主体各自有一套行语法**：栏高、内边距、附加行（预览标题栏 / 结果统计栏 / 选材卡片）都是各写各的，于是三栏的「第一行正文」实测相差 **59px**（337 / 317 / 278）；再叠加**左栏预览被 `max-h-96 + max-h-[320px]` 硬封顶**（596px 高的栏里有 **260px 永久空白**）与**分页条被放进滚动容器内部**（占掉列表视口 58px，且 20 条/页时会被推到折叠线以下），整体就读作「混乱 + 错位」。修复方向不是调几个数值，而是给这个弹窗**立一套共用行语法**（等高栏头 / 统一 24px 内边距 / 三栏固定底条 / 分页移出滚动区 / 预览撑满本栏）。

## 三、根因分析（Root cause analysis）

### 3.0 渲染骨架与实测对账

弹窗纵向是「页头 80 + 页签 68 + 搜索行 76 + 三栏主体 + 底栏 74」：

| 区块 | 代码 | 期望高度 | 实测高度 |
|---|---|---|---|
| 页头（标题 + 副标题） | `VideoSearchModal.tsx:318` `px-6 py-4` + 两行文字 | 80 | **80**（y 2..81） |
| 视频库页签 | `:341` `px-6 py-3` + `p-1` + `py-2` | 68 | **68**（y 83..150） |
| 搜索控制行 | `:367` `px-6 py-4` + 输入 `py-3` | 76 | **76**（y 152..227） |
| 三栏栏头 | `:494` / `:665` / `:907` | 44 / 44 / 50 | **42 / 42 / 48**（y 229..270 / 229..270 / 229..276） |
| 左栏预览标题栏 | `:501` `px-4 py-3` + 标题 + 作者 | 64 | **64**（y 272..335） |
| 中栏结果统计栏 | `:671` `px-4 py-3` | 44 | **44**（y 272..315） |
| 左栏媒体盒 | `:514` `min-h-[200px] max-h-[320px]` | ≤320 | **320**（y 353..672） |
| 中栏分页条 | `:846-899`（在 `:684` 的滚动容器内） | 58 | **58**（y 875..932） |
| 底栏（按钮） | `:988` `px-6 py-4` + 按钮 40 | 74 | **74**（y 934..1007） |

表格的意义：**代码里每一块的 padding / 行高都能与实测高度逐项对上（误差 ≤2px）**，说明截图与当前 HEAD 的样式体系一致，下面的定位不是猜的；同时也直接暴露了问题——**同一「行」在不同栏里高度不同**。

### 3.1 根因 A（主因）：三栏各有一套行语法，正文起点相差 59px

三栏是三个并列的 `w-1/3` flex 列（`:493` / `:663` / `:904`），但栏内结构各不相同：

```tsx
// 左栏 VideoSearchModal.tsx:493-513
<div className="w-1/3 border-r border-border flex flex-col bg-muted">
  <div className="px-4 py-3 border-b border-border bg-muted">      // ← 栏头 44px
    <h4>视频预览</h4>
  </div>
  <div className="flex-1 flex flex-col bg-card">
    <div className="px-4 py-3 border-b border-border bg-muted">    // ← 额外一条 64px 预览标题栏（只有左栏有）
      <h5>{title}</h5><div>{author}</div>
    </div>
    <div className="flex-1 p-4 max-h-96 overflow-y-auto">          // ← 预览滚动区

// 中栏 VideoSearchModal.tsx:663-684
<div className="w-1/3 border-r border-border flex flex-col">
  <div className="px-4 py-3 border-b border-border bg-muted">      // ← 栏头 44px
    <h4>搜索结果</h4>
  </div>
  {allCurrentResults.length > 0 && (
    <div className="px-4 py-3 ... flex items-center justify-between">  // ← 额外一条 44px 统计栏（条件渲染）
  )}
  <div className="flex-1 overflow-y-auto">                          // ← 列表滚动区

// 右栏 VideoSearchModal.tsx:904-923
<div className="w-1/3 flex flex-col bg-muted">
  <div className="flex flex-col bg-card h-full">                    // ← 多套一层
    <div className="px-6 py-3 border-b border-border bg-muted">      // ← 栏头 48px（px-6 而非 px-4）
      <h4>已选择的视频</h4><span className="...">{n} 个</span>
    </div>
    <div className="flex-1 overflow-y-auto">
      <div className="p-3 space-y-2">                                // ← 列表内边距 12px
```

三处差异叠加的结果（实测）：

| 栏 | 栏头高 | 栏头之后第一块 | 正文起点 |
|---|---|---|---|
| 左 · 视频预览 | 42 | 预览标题栏 64（`:501`） | **337** |
| 中 · 搜索结果 | 42 | 统计栏 44（`:671`，无结果时不渲染） | **317** |
| 右 · 已选择的视频 | 48（`:907` 用 `px-6` + 徽章） | 卡片 `p-3` | **278** |

→ 三栏「正文」最大相差 **59px**，且这个差值是**动态的**：中栏统计栏在有/无结果之间切换时，中栏正文会在 317 与 361 之间跳 44px，而左右两栏纹丝不动。用户看到的「错位」首先就是这一条。

**横向也没有公共网格**（实测标题第一个字形的左内边距）：左 15px、中 15px、右 **24px**（`:907` 的 `px-6`）。右栏标题比它自己的卡片（12px）多缩进 12px、比邻栏标题多缩进 8px。

### 3.2 根因 B：左栏预览被 `max-h-96` + `max-h-[320px]` 双硬顶钉死

```tsx
// VideoSearchModal.tsx:513-514
<div className="flex-1 p-4 max-h-96 overflow-y-auto">                    // ① 上限 384px
  <div className="w-full h-full min-h-[200px] max-h-[320px] ...">        // ② 上限 320px、下限 200px
// VideoSearchModal.tsx:592-596（官方库分支；YouTube 分支 :550-554 同款）
<video className="w-full h-full max-h-[320px] object-contain"
       style={{ maxWidth: '100%', maxHeight: '320px' }} ... />
```

两个问题叠在一起：

1. **`max-h-96` / `max-h-[320px]` 与栏高无关，而且是两道彼此独立的封顶**（评审节点用无头 Chrome 复刻同一串 flex 约束实测，V=窗口高 1208 时：栏体 665 → 预览标题栏 64 后剩 601，但 `max-h-96` 把滚动区钉在 **384**，滚动区内 `p-4` 减去 32、媒体盒再被 `max-h-[320px]` 钉在 **320**）：

   | 死空白来源 | 高度 | 代码 |
   |---|---|---|
   | 滚动区之外的自由空间（`flex-1` 想长到 601，被 `max-h-96` 截在 384） | **217px** | `:513` `max-h-96` |
   | 滚动区内部：`p-4` 下内边距 16 + 盒高上限差（352−320）32 | **48px** | `:513` `p-4` + `:514` `max-h-[320px]` |
   | 合计 | **265px**，与实测白区 260px（y 673..932）相符（±5px 为栏头行高取整差） | |

   > **本评审修正**：原文此处写的是 `596 − 64 − 32 − 320 = 180px`，把「栏体 596」当成滚动区高度，即**漏掉了 `max-h-96` 这一道封顶**，也无法解释自己实测到的 260px。真实机制是**两道封顶串联**：`max-h-96` 先把滚动区截断在 384（于是 217px 变成滚动区之外、内容够不着也填不满的死区），`max-h-[320px]` 再在滚动区内部留 48px。这决定了修法——**只删一个 `max-h` 都不够**：只删 `:514` 的 `max-h-[320px]`，盒最多长到 352（=384−32），267px 空白照旧；只删 `:513` 的 `max-h-96`，盒仍被 `:514` 钉在 320。**栏越高，空白越多**——这正是「拉高窗口预览也不变大」的直接原因。
2. **`h-full`（`height:100%`）在这条链上解析不出来**。媒体盒在 `flex items-center justify-center` 的 auto 高度父级里，`h-full` 表现为 `auto`；盒高实际由 `min-h/max-h` 与内容固有尺寸夹取。再叠 `object-contain`：源比例 ≠ 盒比例时画面在**灰盒（`--muted` #F0F0F0）内部 letterbox**，灰边与画面边不重合（实测盒顶灰边 50px、画面下沿直接贴盒底），观感就是「画面缩小 + 漂在灰块里」——S2、S3 同源。

   **补充证据（评审节点新增，决定性）**：真正把画面按死的不止外层容器，**`<video>` 元素自己还有一份硬编码上限，而且是 inline style**：

   ```tsx
   // VideoSearchModal.tsx:592-596（官方库）
   <video src={...}
          className="w-full h-full max-h-[320px] object-contain"   // ← class 上限
          style={{ maxWidth: '100%', maxHeight: '320px' }}         // ← inline 上限（优先级更高）
          controls ... />
   // VideoSearchModal.tsx:550-554（YouTube 就绪态）—— 同一份硬编码
   ```
   inline `maxHeight` 的优先级高于任何 Tailwind class，**只要这两行 inline style 还在，外层容器改成 `flex-1` 也不会让画面变大**，`object-contain` 只会让画面在变大的盒子里重新居中。这是 §五 方案 A 第 5 步原文没有写到的必须动作（见 §九 三·E1）。

   反证就在同一个文件里：无 video_url 的降级分支 `:633` 用的是 `max-w-full max-h-full object-contain`——**正确写法已经在文件里，只是另外两处没有采用**。这既印证「三栏各写一套」的根因，也说明该修法在本文件内已有先例，风险低。

> 这是本仓库**第二次**踩同一个坑：`docs/diagnoses/preview-video-not-filling-container/analysis.md` 已记录「比例帧无 `flex-grow`/`height:100%`，被 `min-height:200px` 钉死」的同类结论。本弹窗只是同一个反模式在另一处的复现（这次还多了一条 `max-h` 上限）。

### 3.3 根因 C：分页条被放进滚动容器内部

```tsx
// VideoSearchModal.tsx:684 —— 打开滚动容器
<div className="flex-1 overflow-y-auto">
  ...结果卡片...
  // :846-899 —— 分页条在它内部
  {totalPages > 1 && allCurrentResults.length > 0 && (
    <div className="px-4 py-3 border-t border-border bg-muted">   // ← 实测 y 875..932
      <button onClick={goToPreviousPage}>上一页</button>
      {[...Array(totalPages)].map(...)}                            // ← :864
      <button onClick={goToNextPage}>下一页</button>
    </div>
  )}
</div>                                                             // ← :900 才关闭
```

后果有三条，全部实测/代码可证：

- **分页会滚走**：`pageSize = 20`（`useVideoSearch.ts:91`），一页 20 张卡片远高于视口（实测 558px），分页条被推到**折叠线以下**，用户必须先滚到底才能翻页；而滚动容器把分页条一起滚走，滚回顶部就看不到页码。
- **吃掉列表视口**：分页条 58px 常驻在滚动盒底部 → 中栏列表视口 = 558px，而左右两栏的是 596px，**同排三栏的底部边界不齐**（截图中那块灰色分页块只挂在中间一栏）。
- **底部边界随内容跳**：结果从 0 条变 1 条时统计栏出现（+44）、分页出现（−58），中栏视口一次变化 100px 量级。

### 3.4 根因 D：条件区块直接改弹窗纵向预算 → 整窗跳动

弹窗是 `flex flex-col` + `h-5/6`（`:316`，`overflow-hidden`），三栏主体拿剩下的空间。任何一条「插进固定区」的条件内容都会**挤压三栏**，而三栏内部并没有能吸收这种变化的设计：

| 条件区块 | 代码 | 出现时的影响 |
|---|---|---|
| YouTube 网络提示 | `:368` `role="note"`，`mb-3` | 搜索行 +32px → 三栏主体整体下移 |
| 结果统计栏 | `:670-681` | 中栏 +44px（只有中栏动） |
| 底部校验错误块 | `:990-1011` | 底栏 +≈90px → 三栏被压扁，左栏预览跟着缩 |
| 自定义时长输入 | `:423-458` | 搜索行内再加两个 `w-20` 输入 |

### 3.5 根因 E：窄高窗口没有自适应阈值

弹窗固定部分 = 页头 80 + 页签 68 + 搜索行 76 + 底栏 74 = **298px**；三栏主体 = `5/6·V − 298`（V = 窗口可用高度）。左栏最小需要 = 栏头 44 + 预览标题栏 64 + `p-4` 32 + `min-h-[200px]` = **340px**。

- `V < ≈766px`（(340+298) × 6/5）：左栏最小预览都放不下 → 因为弹窗是 `overflow-hidden`，超出部分被**裁切**，不会滚动。
- `V < ≈910px`：媒体盒连 320px 上限都拿不到，只能退到 200px 下限，画面更小。
- 用户截图是 `V ≈ 1208px`（弹窗 1007px），早已「够高」，却依然只显示 320px —— 说明 **B（死上限）与 E（无阈值）是两个独立缺陷**，只修一个不够。

**评审节点实测复核（无头 Chrome 复刻 :316/:491/:493/:497/:513/:514 的同一串 flex 约束，改窗口高扫一遍）**：

| 窗口高 V | 弹窗高 | 底栏 top/bottom | 底栏是否被裁 | 左栏滚动区高 | 媒体盒高 | 预览底部被裁 |
|---|---|---|---|---|---|---|
| 1208（用户） | 1007 | 933 / 1007 | 否 | 384（`max-h-96` 生效） | 320 | 0 |
| 900 | 750 | 676 / 750 | 否 | 344 | 312 | 0 |
| 800 | 667 | 593 / 667 | 否 | 261 | 229 | 0 |
| **766** | 638 | 564 / 638 | 否 | **232** | **200（触 `min-h-[200px]` 下限）** | 0 |
| **700** | 583 | 509 / 583 | 否 | 232 | 200 | **≈55px（媒体盒下沿 548 > 栏底 509）** |
| 640 | 533 | 459 / 533 | 否 | 232 | 200 | **≈105px** |

两条结论（都用实测取代原文的纯算术）：

1. **底栏按钮不会被裁**——`:491` 的 `overflow-hidden` 使它的自动最小尺寸规则不生效（CSS 规范：`overflow` 非 `visible` 时 `min-height:auto` 取 0），所以被压的是栏内部，而不是把「确认添加」挤出弹窗。原文「超出部分被裁切」描述正确，**严重度不必上调**（评审节点原本怀疑这里会丢主按钮，实测证伪，记录在案以免下一节点重复怀疑）。
2. **阈值 766px 精确成立**，机制是 `min-h-[200px]` + 栏头/标题栏/内边距的固定和 340px。原文的 `(340+298)×6/5` 算术与实测一致。

**但要注意修完之后的性质变化**：方案 A 第 5 步去掉了 `min-h-[200px]`，等于把 S7 从「裁切」变成「等比缩小」——实测 V=700 时盒高 177、V=640 时仅 **95px**。**缩到 95px 的预览在「顶级产品」语境下不可接受**，因此方案 A 落地时必须二选一（原文未指定，见 §九 三·E4）：保留一个软下限 `min-h-[140px]` 并允许该栏滚动，或对 `V < 760px` 走「预览叠在列表上方」的单栏态（即原文 §八 开放问题 4 的容器查询）。

### 3.6 附带：`w-1/3` 没有 `min-w-0`

三栏都是 `w-1/3`（`:493`、`:663`、`:904`），没有 `min-w-0` / `basis-0`。flex 项默认 `min-width:auto`，中栏卡片里的**长标题**（YouTube 频道名、Pexels 作者名）会把该栏撑宽，三栏不再等宽（`flex-shrink` 只在需要收缩时作用于基准尺寸）。当前截图三栏实测 424 / 424 / 426（正常），但这是数据恰好没超长，不是布局保证。

### 3.7 附带（功能性后果）：切库不重置页码 → 死路

- `useVideoSearch.ts:90-95`：`currentPage` 与 `totalPages` 是**两个库共用**的一份状态。
- `useVideoSearch.ts:755-767 handleLibrarySwitch`：只 `setActiveLibrary` + 清预览，**没有 `setCurrentPage(1)`**。
- `VideoSearchModal.tsx:273-278 getCurrentResults()`：按 `currentPage` 对**当前库**的结果做切片；而统计栏与分页条只看 `allCurrentResults.length`（`:670`、`:846`）。

于是：官方库停在 3 页 → 切到 YouTube（结果只有 1 页）→ `slice(40,60)` 为空 → 列表渲染「开始搜索」空态，但统计栏说「找到 N 个」、分页条仍在（1/3）。**结果存在却看不见，也没有页码可点回去**。这是「布局/状态耦合」造成的可用性缺陷，与 S1–S5 同一批改动顺带修掉最划算。

> **本评审修正（原文此处自相矛盾）**：`totalPages` 是**按当前库**算的（`useVideoSearch.ts:92-95` 只依赖 `activeLibrary` 与两个结果数组的长度），切到 YouTube 之后 `totalPages = ceil(N_youtube/20)`。所以上面的例子不可能同时出现「分页条仍在（1/3）」和「统计栏说找到 60 个」：
> - 若 `N_youtube = 8` → `totalPages = 1` → **分页块整块不渲染**（`:846` 要求 `totalPages > 1`）→ 用户看到「找到 8 个视频 / 已选择 0」的统计栏 + 「开始搜索」空态 + **没有分页**，`currentPage` 仍卡在 3，**连点回去的入口都没有** → 比原文描述的更死。
> - 精确触发条件：**`currentPage ≥ 3` 且切库后 `N_new ≤ 40`**（即新库页数 < 旧库当前页）。两条链路都会撞上：YouTube 搜索结果少于 41 条时（含搜索失败/部分失败后的残留结果），以及反方向「YouTube 3 页 → 切官方库只有 ≤40 条」。
> - 只把症状写成「分页条仍在但页码错」会诱导下一节点只做「页码夹取（clamp）」而不重置，**clamp 到 `totalPages` 仍会在下次切库时复发**；必须按 §六 第 5 步 `handleLibrarySwitch` 里 `setCurrentPage(1)`（根因是「一份页码状态被两个库共用」，而不是「页码越界」）。
> - 落点提醒：`VideoSearchModal.tsx:296-303` 有一个**同名**的本地 `handleLibrarySwitch`（只 `setActiveLibrary` + 打日志），它接收的 prop `setActiveLibrary` 其实是 hook 里那个 `handleLibrarySwitch`（`useVideoSearch.ts:833` 的映射）。**要改的是 hook 里那一个（`useVideoSearch.ts:755-767`）**，否则改到组件里的同名函数等于没改——这是下一节点最容易踩的坑。

### 3.8 截图对应的构建（原「未定论」，评审节点已定案：旧构建）

原文观察成立：同一帧里同时出现「正在搜索视频…」转圈、统计栏（「找到 60 个视频 / 1 已选择 / 1 3」）、分页条（1/2/3）与**已加载完成的左栏预览**（播放器显示 `0:00 / 0:09`）。按 HEAD 代码这确实不可能，但原文把它留作两种解释。**评审节点直接看图即可定案，不必等到实施期加日志**：

```tsx
// useVideoSearch.ts:299-302 —— handleSearch 在 await 之前就同步清空
setIsSearching(true);
setSearchResults([]);      // ← 结果清零
setPreviewVideo(null);     // ← 左栏预览同时被清
setCurrentPage(1);
// ... await videoSearchService.searchVideos(...)
```

- 三个 `setState` 与 `setIsSearching(true)` **在同一个事件回调里同步执行**，React 18 会在事件结束、浏览器绘制之前一次性提交 → **不存在任何一帧**能同时画着「转圈」和「已加载的预览/统计栏」。第 2 种解释（抓到状态切换的瞬态帧）可以排除。
- 截图里左栏预览不仅存在，还已经 `onCanPlay`（有时长 `0:09`、有播放控件）。若走 HEAD 的 `handleSearch`，预览在搜索**发起的那一帧**就被置空了。
- 结论：**截图来自「搜索时不清空旧结果/旧预览」的历史构建**。因此 §八 开放问题 1 关闭，且「转圈 + 统计栏并存」**不是第二个 bug**，不要写进修复范围。

**顺带改正原文引用的一处数字**：原文说 `[4]` 实测中栏正文着墨率 0.8%、包围盒 88×80。用**本报告自带的脚本、同一张图**复算得到 **20.4% / bbox x433..852 y371..1006**，无法复现 0.8%。原因是脚本 `[4]` 的取样区间是 `(x0+2, x1-2, 正文起点, 弹窗底-2)`（`measure_screenshot.py:216`），**把 y875..932 的 58px 分页带和 y934..1007 的 74px 底栏一起算成了「正文」**，指标被灰色底栏污染，因此它既不能证明也不能否证「中栏只有一个转圈块」。定性判断请以肉眼 + §3.2 的 flex 实测为准，不要再引用 0.8% 这个数。

> 影响面：截图与 HEAD 的**内容态**不同（旧构建），但**壳层结构完全一致**——§3.0 的逐块高度对账、§三 的三栏行语法差异都是按 HEAD 源码读出来的，且 §2.4 节的独立复核已对 HEAD 源码逐行确认。所以本 bug 的根因结论不受构建版本影响，**只有「要不要处理转圈与统计栏并存」这一个议题被关闭**。

### 3.9 附带（评审节点新增）：三栏空态的垂直定位也各写一套，中/右栏的 `flex-1` 是死代码

这是「三栏各有一套行语法」的**第三处**证据，原报告没有记录，但它是用户打开弹窗**第一眼**看到的画面（搜索结果为空、未选择任何视频时），因此对「布局混乱」的贡献不小：**左栏空态垂直居中，中栏和右栏的空态贴在本栏顶部**。

原因只有一行 CSS 语义——`flex-1`（`flex: 1 1 0%`）只对 **flex 容器的子元素**生效，而中/右栏的空态是**块级滚动容器**的子元素：

| 栏 | 滚动容器（父） | 空态（子） | `flex-1` 是否生效 | 实测空态位置 |
|---|---|---|---|---|
| 左 | `:497` `flex-1 flex flex-col`（**flex 列**） | `:649` `flex-1 flex items-center justify-center` | **生效** | 垂直居中（上 225 / 下 226，无头实测） |
| 中 | `:684` `flex-1 overflow-y-auto`（**block**） | `:834` `flex-1 flex items-center justify-center p-8` | **失效**（父不是 flex 容器） | **贴顶**（上 32 = `p-8`，下方空 419px，无头实测） |
| 右 | `:921` `flex-1 overflow-y-auto`（**block**） | `:972` `flex-1 flex items-center justify-center p-4` | **失效** | **贴顶**（同类结构） |

> 注意「搜索中」的转圈态 `:686` 用的是 `h-full` 而不是 `flex-1`，所以它**是**居中的（截图可证）——同一个中栏里，转圈态居中、空态贴顶，两种状态之间还会跳一次位置。这也是「错位」的一部分。

**复现/复核命令**（评审节点用无头 Chrome 实测，脚本不进入仓库，等价断言如下）：把 `:684`/`:921` 改成 `flex-1 flex flex-col`（或给空态包一层 `min-h-full`），空态即回到垂直居中。

**对修复方案的影响**：§五 方案 A 的第 1–3 步只重排「栏头 / 滚动体 / 底条」，**没有一条覆盖空态**。若照原样实施，空态贴顶会原封不动留下来，下一轮验收仍然会被判「乱」。因此方案 A 必须补一条（见 §九 三·E2）。

## 四、影响面（Impact surface）

**受影响用户**：所有用「脚本面板 → 搜索在线视频 → 添加合成」找素材的用户（官方视频库 + YouTube 视频库两条链路都受影响，两者共用同一套三栏骨架）；桌面端与浏览器调试路径表现一致（同一组件 + 同一 Chromium 渲染）。

**受影响功能**：

1. **素材挑选效率**：预览只有 320px 高且下方大片空白 → 竖屏素材几乎看不清构图；「确认添加」前无法判断画面。
2. **分页可达性**：20 条/页时翻页必须滚到底；滚回顶部后页码消失，用户容易以为只有一页。
3. **可读性/信任感**：三栏标题不在一条线、内边距 16/16/24 混用、底部灰块只挂中间一栏 → 整个弹窗显得「拼起来的」，与「顶级产品」的定位直接冲突。
4. **窄窗口不可用**：笔记本 + 分屏（窗口高 < 766px）时左栏预览被裁切。
5. **状态死路**（S8）：切库后可能出现「有结果但看不见、也无页码可点」。

**不受影响**：搜索请求、时长校验、下载/入库等业务逻辑（本 bug 是表现层 + 一处分页状态，不动数据流）。

## 五、候选修复方案（Candidate fixes）

### 方案 A（推荐）：给三栏立一套共用行语法，就地重排

不动业务逻辑，只重组三栏骨架 + 改 5 处尺寸约束：

1. **栏头契约**：三栏栏头统一 `h-11`（44px）+ `px-6`（24px），只放「标题 + 右侧元信息」一行；
2. **元信息降级**：中栏「找到 N / 已选 M」从独占 44px 行降级为栏头右侧 chip（`:670-681` 整块移除）；左栏「标题 + 作者」从 64px 标题栏降级进本栏底条（或叠加在预览画面上）；
3. **三栏固定底条**：三栏各有一条等高（如 52px）的 `shrink-0` 底部区，左=素材信息/预览开关，中=分页，右=「已选 N · 合计时长」+ 清空 → 滚动视口底边与底条同时对齐；
4. **分页移出滚动容器**：把 `:846-899` 从 `:684` 的 `overflow-y-auto` 内提到其**兄弟**位置；
5. **预览撑满**：`:513-514` 去掉 `max-h-96` / `max-h-[320px]` / `max-h-[200px]` 链，改成 `flex-1 min-h-0` + 媒体 `h-full w-full object-contain`，媒体盒背景只在「无画面」时用；YouTube 分支（`:550-554`）同改；
6. **条件区块不再改预算**：YouTube 提示并入搜索行已有高度（或做成输入框下方 reserved 一行）；校验错误块改为**浮层**（absolute + 底部上方）或固定在底栏之下的独立区，不挤压三栏。

### 方案 B：只做外科手术（最小改动）

只改 4 个数/4 个类：删掉 `max-h-96`、删掉媒体盒 `max-h-[320px]`、分页移出滚动容器、右栏 `px-6`→`px-4`。**不**统一栏头高度、**不**动统计栏。

### 方案 C：抽 `SearchPanel` 组件 + 设计令牌（最彻底）

把「栏头 / 滚动体 / 底条」抽成 `<SearchPanel header={} footer={}>`，三栏只用它拼装；内边距、栏头高、底条高来自同一组 token（例如 `--panel-pad: 24px`、`--panel-head: 44px`、`--panel-foot: 52px`）。同时把左栏预览做成 `<PreviewStage aspect="contain" />`（内部 `flex-1 min-h-0`）。

## 实施过程发现的方案缺陷（Issues Found During Implementation）

> **实施节点**：Subtask #2。本节只记录「照 §九 四 的 A′ 逐条实施时，方案本身没写清、或写清了但按字面做会引入新缺陷」的部分，以及**实际改法**与**实测证据**。定案（A′ + E0–E9、S8 拆独立补丁）本身未被推翻，下列 5 条是它的收敛补丁。

### 一、校验错误浮层会遮住中栏分页（已修正，属阻断级）

§九 四 第 4 步只写了「校验错误块改为不挤压三栏的浮层（absolute + 底部上方）」，未规定**锚点与宽度**。按字面写成 `absolute bottom-full left-0 right-0`（横贯弹窗整宽）时，浮层正好压在**中栏 52px 底条**上——也就是 E3 好不容易才做出来的「分页常驻可见」被它盖住。

- **证据**：无头 Chrome 1288×1208 截图，浮层 y≈928..1013 覆盖中栏底条 y≈888.6..940.6，「上一页 1 2 下一页」整块被遮。
- **实际改法**：锚定到右下角并限宽——`absolute bottom-full right-6 mb-2 w-[min(36rem,calc(100%-3rem))]`，另加 `role="alert"`。浮层只覆盖它所属的操作区上方，中栏底条与右栏底条全程可见。
- **教训**：「浮层不挤压布局」与「浮层不遮挡关键控件」是两条独立要求，方案只写了前者。

### 二、判据②「滚动视口底边 y 相等」的取样元素随状态变化，必须改成量底条顶边

判据② 原文要求「三栏列表滚动视口底边 y 相等」。但实施后发现**这个元素并不总存在**：

- 左栏只有在**有预览**时才渲染 `:513` 那个 `flex-1 min-h-0 overflow-y-auto` 滚动体；无预览时它是一个居中空态 div（`flex-1 flex items-center justify-center`，**不是**滚动容器），底下才是 52px 底条。
- 中/右栏的滚动体则始终存在。

所以按「滚动容器的底边」取样，会在左栏空态下取到**另一个元素**，得到假通过（自比自）。这不是样式缺陷，是判据口径缺陷。

- **实际改法**：三栏统一打 `data-pane` / `data-pane-head` / `data-pane-scroll` / `data-pane-foot` 四个锚点；判据② 改为量 **`data-pane-foot` 的 `top`**（三栏底条等高且无条件渲染 ⇒ 等价于「内容区底边对齐」，且在空态/搜索中/单页下口径一致）。结构契约测试 `VideoSearchModal.youtube.test.tsx` 复用同一组锚点。
- **实测**（无头 Chrome，7 种状态 × 4 种窗口）：`headBottom`、`footTop`、`titlePad` 的三栏差 **恒为 0**。

### 三、E4「软下限 + 该栏可滚动」与「栏内死空白 ≤24px」必须一起读

按 E4 第一方案保留 `min-h-[140px]` 后，极窄高度下媒体盒（140）加上 `p-4`（32）会**超出**滚动视口：

| 窗口 | 视口 V | 左栏滚动视口高 | 媒体盒高 | 溢出（需滚动）量 |
|---|---|---|---|---|
| 1288×1208 | 1109 | 508 | 476 | 0（撑满） |
| 1288×1400 | 1301 | 668 | 636 | 0（撑满） |
| 1288×800 | 701 | 168 | 140 | **4px** |
| 1024×768 | 669 | 141.3 | 140 | **30.7px** |

靠 E7 保留的 `overflow-y-auto`，这是**可滚动的 4–31px**，不是裁切，符合 E4 的「软下限 + 允许该栏滚动」。但验收时若把「栏内死空白 ≤24px」当成「任何情况下都不得有滚动」，会误判为失败——**该判据只针对 `max-h` 造成的结构性空白**，与 `min-h` 造成的滚动范围是两件事。

### 四、改完上限后，日志仍在自述 320px 上限（已修正）

`:566` / `:613` 两处 `logger.info` 的载荷里还留着 `previewContainerMaxHeight: '320px'` 与 `layoutType: 'constrained_height_preview'`。上限已删而日志照旧，等于在埋**误导下一轮诊断的证据**（本 bug 的 §3.8 就是被同类「旧构建/旧日志」证据拖住过一轮）。

### 五、§九 四 第 1 步「左栏标题进底条」与右栏底条的信息重叠（已按不重复原则落地）

左栏底条若放「标题 + 作者」，右栏底条再放「已选 N · 合计时长」，会让右侧栏头徽章（`N 个`）与右栏底条（`N 个`）**重复计数**。

## 代码评审（Subtask #3）

> **评审节点**：Subtask #3（对 Subtask #2 的改动做逐条评审、就地修正并提交）。
> **评审方式**：把 `git diff` 与 §九 四 的 A′ 八步逐条对账；对每条改动追问「命中根因还是掩盖症状 / 是否在相邻路径引入回归」；然后**重跑** type-check、组件测试、Tailwind 编译与几何推导。下列 6 条是评审期发现并已就地修正的问题，均不推翻 A′ 定案。

### 一、阻断级：校验错误浮层按 36rem 限宽仍会压住中栏分页（已修正）

§实施六 一只修到「浮层不挤压纵向预算」，宽度写的 `w-[min(36rem,calc(100%-3rem))]`。按 A′ 的判据 ② 复算几何：弹窗内容宽 W（`max-w-7xl` = 1280）、三栏各 W/3，浮层右对齐 `right-6`（24px）、宽 576px → 左边缘在 `W-24-576 = 680`，而中栏底条横跨 `W/3..2W/3 = 427..853`，**「上一页 / 下一页」组居中于 640±116 = 524..756 → 被判据要保住的分页按钮被压掉 76px**。W=1024 时同样重叠。

- **实际改法**：宽度收成 `w-[min(24rem,calc(33.333%_-_3rem))]`（本栏内宽减去两侧留白）。几何证明：左边缘 = `W-24-(W/3-48) = 2W/3+24`，恒等于右栏左边缘 +24px ⇒ **任何窗口宽度下浮层都严格落在右栏内，中栏底条与分页零遮挡**；`min(24rem, …)` 只在 `W>1296` 时生效，条件同上。
- **验证**：Tailwind 编译确认该类产出 `width: min(24rem,calc(33.333% - 3rem))`（`_` → 空格）；新增断言锁定「含 `w-[min(24rem`、不含 `36rem`、不在中栏底条内」。
- **教训**：「不挤压布局」与「不遮挡别的栏」是两条独立要求，只写前者时，横贯整窗的浮层必然越界。

### 二、一致级：中栏统计 chip 与右栏徽章会报出两个不同的「已选择」数（已修正）

统计行降级为 chip 时沿用了旧的 `currentSelectedResults.size`，而右栏徽章用 `selectedVideos.length`。两者**在正常操作下就会分叉**：`handleSearch` / `handleYoutubeSearch` 只清空结果与预览（`useVideoSearch.ts:299-302`、`:339-342`），**并不清空选中集合**；于是「先选 A（结果 1）→ 用新关键词重搜 → A 不在新结果里」时，chip 显示「已选择 1 个」而右栏列表为空、徽章为 0。同一弹窗两处计数互相矛盾，是本轮新增 UI 才暴露的可信度缺陷。

- **实际改法**：抽出纯函数 `formatResultsSummary(template, resultCount, selectedCount, isYoutube)`（模块级，附 JSDoc），两处数字同源取 `selectedVideos.length`（当前库中**可见**的已选条数）。顺带收拢占位符替换产生的双空格与首尾空白。
- **验证**：新增用例传入「结果 2 条 + 选中集合含 1 条已消失的 id」，断言 chip 与徽章都报 1 —— 旧实现必红。

### 三、健壮性：底条规格会把 `undefined × undefined` 写进界面（已修正）

左栏底条新增了「分辨率 · 时长」，其中 `width/height` 来自搜索结果映射（`useVideoSearch.ts:567`、`:599-600` 等），**并不保证存在**；旧标题栏只显示标题与作者，所以这条缺陷是本轮新引入的。

- **实际改法**：`previewSpecText` 按字段是否真的存在拼接 `分辨率 • 时长`，两个都缺失时整段不渲染。

### 四、清理：`foundVideos / items / selected` 三个翻译键成为死键（已删除）

统计行移除后，`videoSearchModal` 命名空间下这三个键在全仓已无引用（`grep` 仅命中定义处）。i18n 是单一来源文件，留死键会让下一个人以为「统计行还在」。

- **实际改法**：接口 + 英文 + 中文三处一并删除；`itemsUnit`（右栏徽章仍在用）保留。`npx tsc --noEmit` 通过，`Translations` 的完整性由类型系统兜住。

### 五、结构：右栏栏头多套了一层 `flex justify-between w-full`（已展平）

三栏栏头要「同一套行语法」，但右栏栏头内还包了一层 `div`（历史遗留）。展平后三栏栏头结构完全同构：`h-11 px-6 flex items-center justify-between gap-3` + `h4` + 右侧元信息。

- 同时把中/右栏标题改为 `shrink-0`（四个字的固定标签永不让位），由可截断的 chip / 徽章让位，避免窄窗下先被省略号吃掉的是栏标题。

### 六、YouTube 失败态容器：`m-auto` 居中需要 flex（已修正）

失败态（缩略图 + 文案 + 重试 + 外链）搬进 `w-full h-full overflow-y-auto` 后，内层写 `m-auto` 想实现「放得下居中、放不下滚动」，但 `m-auto` 只在 flex/grid 容器里才产生垂直居中。改为 `flex ... overflow-y-auto` + 内层 `m-auto`，两个目标才同时成立；顺带把该分支的缩进补齐（原实现多一层 `div` 后未重排，读起来像少了一个闭合标签）。
